검토용 구현 계획

DeliveryBot Python Policy Simulator 구현 방향

현재 구현된 DeliveryBot, Python 정책 서버, Docs, Json/Input을 기준으로 정리한 정책 실험용 가상 환경 고도화 계획입니다.

결론: Unreal은 환경, 물리, 센서, 평가를 책임지고 Python은 길찾기, 정책 판단, 재계획, 제어 명령 생성을 책임지는 현재 구조를 유지합니다.
기준일 2026-06-10 UE 5.7 Runtime Module HTTP Policy Loop Grid A* + DWA Episode JSON Pair 실행
핵심 판단

새 구조를 만들기보다 현재 축을 고도화한다

이미 잡힌 중심축

  • ADeliveryBot은 센서 관측과 이동 명령 실행을 담당합니다.
  • UDeliveryBot_PolicyControllerComponent가 policy loop, startup spec, version 검증을 관리합니다.
  • Tools/PythonPolicyServer가 catalog, policySpec, A*, DWA, 동적 장애물 overlay를 담당합니다.

고도화가 필요한 부분

  • Python planner 계층을 A*, Hybrid A*, DWA 단위로 명확히 분리합니다.
  • 장애물 의미 판정은 ActorTags에서 Semantic DataAsset 기반으로 확장합니다.
  • 정책 조합 실험은 JSON 파일 임시 방식에서 UI 또는 Web 설정 흐름으로 옮깁니다.

현재 문서 일부에는 이전 TODO가 남아 있으나, 코드 기준으로 actorTags 전송, policy registry, DWA, dynamic obstacle overlay는 이미 반영되어 있습니다.

현재 런타임 시퀀스

Episode 시작부터 주행 명령까지

1. 입력 선택 RunQueue가 ScenarioSetup과 DeliveryBotSetup pair를 지정합니다.
2. Grid 생성 GroundRegion 기반 Runtime GridBoundsActor를 만들고 GridSubsystem이 cell을 분류합니다.
3. Robot spawn EpisodeSimulationSubsystem이 BP_DeliveryBot 또는 C++ class를 spawn합니다.
4. Python 동기화 Startup PolicySpec 전송 후 /episode/start로 grid/config/start/goal을 보냅니다.
5. Policy loop /policy/action 응답을 검증하고 target speed, steering, brake를 적용합니다.
현재 사실 계획 반영
BuildEpisodeStartJson()은 grid/config/start/goal을 포함하지만 policySpec은 별도 startup 파일로 먼저 전송합니다. 단기에는 이 흐름을 유지하고, 정책 UI/Web 결정 후 /episode/start 포함 여부를 다시 판단합니다.
Python 응답에는 episodeVersion, configVersion, gridVersion이 포함됩니다. 모든 새 planner와 policy도 동일한 version 계약을 깨지 않아야 합니다.

Python 구현 상태

정책 엔진은 이미 priority 기반 후보 선택 구조

정책 실행 흐름

  1. 서버가 episode/config/grid/policySpec을 메모리에 저장합니다.
  2. Observation이 들어오면 runtime context를 구성합니다.
  3. enabled policy evaluator만 실행합니다.
  4. 각 policy는 action 후보를 반환하거나 상황이 아니면 반환하지 않습니다.
  5. priority 숫자가 가장 낮은 후보를 최종 action으로 선택합니다.

현재 policy 목록

  • front_obstacle_stop: hard stop, TTC, recovery, sustained reroute
  • reroute_when_blocked: A* 실패 시 정지 후보
  • dwa_local_avoidance: LiDAR hit 기반 short-horizon 회피
  • front_obstacle_slowdown: 감속 + dynamic obstacle overlay
  • normal_path_follow: Grid A* + lookahead steering

Python은 아직 모듈명이 단순하지만, 기능적으로는 global planner, local planner, behavior policy가 한 서버 안에서 동작합니다. 다음 단계는 이 책임을 파일/인터페이스 단위로 더 선명하게 분리하는 것입니다.

JSON 입력 해석

실험 단위는 ScenarioSetup + DeliveryBotSetup + PolicySpec

ScenarioSetup_scenario_001_000.json

  • 14m x 8m 보도 baseline scenario
  • 북쪽 curb penalty, 남쪽 storefront blocked region
  • mailbox, bench 정적 장애물
  • parallel pedestrian path
  • robot start [-5.5, -1.5], goal [5.5, -1.5]

DeliveryBotSetup_scenario_001_000_baseline.json

  • max speed 8.0 km/h
  • path target speed 6.5 km/h
  • lookahead 1.2m
  • LiDAR range 5.5m
  • stop 1.0m, slowdown 3.2m
정책 실험 입력 의미
PolicySpec_DefaultDelivery.json stop, reroute, DWA, slowdown, normal path follow를 함께 사용합니다.

PolicySpec_AStarPolicyOptionsExample.json 정책별 A* cost, diagonal, dynamic obstacle, recovery 옵션 검증용입니다.

길찾기 스택

A*, Hybrid A*, DWA의 책임을 분리한다

계층 현재 상태 추가 구현 방향 출력

분리 기준

  • Planner는 policy를 모릅니다. grid, pose, goal, 옵션을 받아 path 또는 command 후보만 냅니다.
  • Policy는 planner 결과를 고르고, 안전/양보/재시도 규칙을 적용합니다.
  • World model은 observation을 누적하고 TTL, inflation, semantic class를 관리합니다.
  • Action builder는 계속 한 곳에서 speed/steering/brake 범위를 보장합니다.

현재 pathfinding.py의 A*는 유지하면서 파일을 나누는 방식이 안전합니다. 한 번에 알고리즘을 교체하지 않습니다.

3단계

Hybrid A*는 Python의 pose planner로 구현한다

왜 필요한가

  • A* grid path는 로봇 회전 반경과 후진을 직접 표현하지 못합니다.
  • 좁은 복도, U턴, 장애물 옆 정렬에는 pose 단위 경로가 필요합니다.

입력

  • grid lookup
  • start pose x/y/yaw
  • goal pose 또는 goal point
  • min turning radius
  • forward/reverse motion model

출력

  • pose path
  • direction per segment
  • path cost와 expanded count
  • fallback reason
구현 원칙 설명
UE C++ 구현은 참고만 FDeliveryBotHybridAStarConfigInfo와 기존 C++ 알고리즘은 옵션/동작 기준으로 읽되, Python policy mode의 최종 판단은 Python에 둡니다.
작게 시작 처음에는 저속 pose path 생성과 debug path 반환을 목표로 하고, DWA와 결합은 다음 단계로 둡니다.
4단계

장애물 의미 판정은 ActorTags에서 Semantic DataAsset으로 확장

현재

  • LiDAR ray와 observed object에 actorTags가 포함됩니다.
  • Python은 가까운 전방 객체와 LiDAR hit를 이용해 stop, slowdown, DWA, dynamic blocked를 판단합니다.
  • 객체가 사람인지, 콘인지, 밟을 수 있는 맨홀인지는 아직 태그 기반 임시 판단 단계입니다.

확장

  • semanticTypeId, objectCategory, mobilityType를 observation에 추가합니다.
  • TraversalType: Block, DriveOver, Penalty, Ignore를 정책 입력으로 사용합니다.
  • 사람과 차량은 dynamic obstacle, 낮은 맨홀/턱은 penalty 또는 speed limit로 처리합니다.
정적 환경은 Grid 생성 시점에 비용화하고, 런타임 객체는 LiDAR 관측 이후 의미와 통과 가능성을 판단합니다.
5단계

정책 프로파일은 policySpec 조합으로 만든다

프로파일 우선 정책 설정 의도 검증 시나리오
사람 우선 pedestrian_stop, pedestrian_slowdown, DWA 보행자 안전과 courtesy metric을 우선합니다. 횡단 보행자, 병렬 보행자, path corridor 점유
로봇 우선 DWA, low-speed grace, normal path follow 충돌 위험이 낮으면 배송 효율과 진행성을 우선합니다. 넓은 보도, 낮은 밀도 장애물, 시간 제한 배송
보수적 배송 hard stop, long slowdown, wide inflation 오탐을 감수하고 안전 여유를 크게 둡니다. 좁은 보도, 가려진 장애물, 연속 static obstacle
A/B 알고리즘 비교 NormalOnly, A*, Hybrid A*, DWA on/off 알고리즘 자체 성능을 정책 효과와 분리해 봅니다. 동일 Episode + 다른 PolicySpec

새 정책을 Python 파일로 추가할 때는 catalog에 displayName, category, defaultPriority, parameters schema를 같이 넣어야 실험 UI로 자연스럽게 올라갑니다.

6단계

제어 명령은 단순하게 유지하고 debug만 풍부하게

Action 계약 유지

{
  "action": {
    "steering": -1.0 ~ 1.0,
    "targetSpeedKmh": 0.0 이상,
    "brake": 0.0 ~ 1.0,
    "direction": "Forward" | "Reverse"
  }
}

Debug 확장

{
  "debug": {
    "selectedPolicyId": "dwa_local_avoidance",
    "pathStatus": "ok",
    "planner": "hybrid_astar",
    "replanReason": "dynamic_obstacle_on_corridor",
    "pathWorldPoints": []
  }
}
  • Unreal은 action 검증과 물리 이동만 담당하므로, 새 제어 방식도 먼저 targetSpeedKmh 중심으로 맞춥니다.
  • Hybrid A*가 direction profile을 반환해도 초기에는 lookahead target을 통해 steering/speed로 변환합니다.
  • 실험 분석에 필요한 정보는 action 필드를 늘리기보다 debug와 report/log에 남깁니다.
평가와 로깅

정책 개발자가 봐야 할 결과를 report로 연결

Safety

  • collision count
  • near miss count
  • min pedestrian distance
  • min TTC

Courtesy

  • forced wait
  • schedule delay
  • path deviation
  • blocked duration

Efficiency

  • goal reached
  • duration
  • idle duration
  • extra path distance

Planner

  • replan count
  • expanded nodes
  • path cost
  • DWA no-safe count

보행자 runtime metric은 이미 core 구현이 진행되어 있으므로, 다음 계획에서는 EvaluationReport JSON과 measurement log로 끌어올리는 작업이 중요합니다.

리뷰 포인트

결정이 필요한 항목

제품/UX 결정

  • 정책 설정 UI를 Unreal WBP로 할지, Web UI로 할지 결정해야 합니다.
  • 정책 개발자가 직접 편집할 JSON과 UI에서만 만질 값을 구분해야 합니다.
  • 실험 결과를 MainMenu에서 미리보기할지, 별도 분석 페이지로 보낼지 정해야 합니다.

기술 결정

  • Hybrid A*의 canonical 구현 위치는 Python으로 두는 것이 현재 목표와 맞습니다.
  • policySpec을 계속 별도 전송할지, /episode/start에 포함할지 정해야 합니다.
  • Semantic DataAsset 도입 전까지 ActorTags 기반 policy를 어디까지 허용할지 정해야 합니다.

리스크

  • Grid 생성 순서가 StaticObstacle spawn보다 앞서면 정적 장애물이 grid에 반영되지 않을 수 있습니다.
  • Python 서버가 꺼져 있거나 늦게 응답할 때 Unreal은 정지 상태로 안전하게 실패해야 합니다.
  • 문서의 오래된 TODO와 현재 코드 상태가 섞여 있으므로 구현 전에는 코드 기준으로 재확인해야 합니다.

방향성

  • Hybrid A*를 Python으로 옮기는 비용과 장점이 맞는가?

  • PolicySpec만 바꾸면 같은 Episode에서 정책 비교가 가능한가?

  • 사람 우선/로봇 우선의 차이가 metric으로 드러나는가?

안전성

  • 서버 지연/끊김/invalid action에서 로봇이 정지하는가?
  • version mismatch나 stale sequence가 이동에 쓰이지 않는가?
  • 동적 장애물 TTL과 inflation이 과도하거나 부족하지 않은가?

운영성
