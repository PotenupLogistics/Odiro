# LLM World Config Generation Flow

After schema validation passes, the flow performs scenario reflection validation. When reflection fails, deterministic scenario post-processing is attempted before a scenario repair prompt is sent back to the LLM client. This keeps obvious scenario fixes, such as Kickboard obstacle insertion or pedestrian crossing behavior, local and schema-bound.

Validated generation results can be wrapped by the UE5 handoff endpoint. The handoff response includes `worldConfig` only when schema validation, contract validation, and scenario reflection pass.

## FastAPI Generation Endpoint

`POST /api/v1/generation/world-config` now calls the internal orchestrator.

At this stage:

- the default provider is `disabled`
- disabled returns `success=false`
- external LLM providers are not implemented
- validation is required before `generatedPayload` can be used
- UE5 handoff is still a later stage

## Generation Orchestrator Status

The internal generation orchestrator is now implemented as a service layer.

- It builds the prompt package.
- It calls the LLM client abstraction.
- It extracts a JSON object from successful LLM content.
- It validates the extracted payload with the `world_config` contract.
- It records repair attempts based on validation errors.
- With the `disabled` provider, it returns a clear failed result without generating a payload.

No external LLM provider is called in this stage, and no FastAPI generation endpoint is added.

## LLM Client Abstraction

After prompt package creation, the prompt package is intended to be passed to the LLM client abstraction.

Current status:

- The default provider is `disabled`.
- No external provider call is made.
- No World Config payload is generated by the disabled provider.
- Provider output must pass the validation layer before any UE5 handoff in a later stage.

Flow at this stage:

Natural Language Prompt

External LLM execution, generated World Config payload return, and UE5 handoff remain later stages.

## Current Implementation Scope

The current implementation stops at prompt package generation.

- `app/services/natural_language_normalizer.py` normalizes the natural-language prompt with deterministic keyword rules.
- `app/services/world_config_rag_context_builder.py` retrieves policy context from `data/rag/policy_rag_chunks.jsonl`.
- `app/services/world_config_prompt_builder.py` builds the system/user prompt package and repair prompt package.
- No external LLM API call is made in this stage.
- No FastAPI endpoint is created in this stage.
- No sample JSON or fixture files are created in this stage.

Repair prompts are generated from validation errors, but the repair loop execution and LLM call remain a later step.

## Deterministic Retrieval Before Embeddings

The MVP generation flow uses deterministic retrieval over `data/rag/policy_rag_chunks.jsonl`.

Retrieval inputs can include:

- normalized prompt keywords
- mapped MVP situation
- target action
- policy parameter names
- source filters when needed

The retrieved chunks become policy context for World Config drafting. Embedding search, vector DB storage, and source document RAG are deferred to later stages.

-> LLM World Config Draft Generation

## 2. 단계별 설명

| 단계 | 입력 | 출력 | 실패 처리 |
| --- | --- | --- | --- |
| Natural Language Prompt | 사용자 시나리오 설명 | 원문 prompt | 입력이 너무 모호하면 추가 질문 |
| Prompt Normalization | 원문 prompt | 구조화된 의도와 제약 | 금지 요청은 거부 또는 범위 축소 |
| Policy/RAG Context Retrieval | 구조화된 의도 | 관련 policy card context | 관련 card가 없으면 기본 World Config 제약만 사용 |
| LLM World Config Draft Generation | prompt, schema 요약, RAG context | World Config draft | JSON이 아니면 JSON Extraction에서 실패 |
| JSON Extraction | LLM 출력 | JSON object 후보 | JSON object가 없으면 repair 요청 |
| Contract Validation | JSON object 후보 | validation layer 결과 | schema/Pydantic 오류를 수집 |
| Repair Loop | validation error | 수정된 JSON object 후보 | 최대 2회까지 repair |
| Validated World Config | 검증 통과 payload | UE5 전달 가능 payload | 검증 전에는 UE5 전달 금지 |
| UE5 Handoff | Validated World Config | UE5 world setup input | 전달 실패 시 로그와 payload id 기록 |

## 3. Validation 원칙

- LLM 출력은 반드시 `world_config.schema.json`을 통과해야 한다.
- Pydantic `WorldConfig` 모델 검증을 통과해야 한다.
- validation 실패 시 에러 메시지를 LLM에 전달해 최대 2회 repair를 시도한다.
- 2회 실패 시 사용자의 입력을 명확히 하도록 요청한다.
- validation 통과 전에는 UE5에 전달하지 않는다.

## 4. RAG 사용 방식

- `policy_knowledge_cards.jsonl`은 LLM이 생성할 World Config의 안전 제약과 시나리오 구성 근거로 사용한다.
- RAG는 공식 인증 준수를 주장하기 위한 용도가 아니다.
- RAG는 프로젝트 내부 정책 기준과 시나리오 제약을 제공하는 용도다.

## 5. 출력 원칙

- LLM은 World Config JSON만 생성한다.
- 설명 문장을 JSON 안에 섞지 않는다.
- schema에 없는 필드는 생성하지 않는다.
- 불명확한 값은 assumptions에 기록하거나 기본값 정책으로 처리한다.

## Prompt Hardening Update

The generation flow now adds a schema-derived World Config checklist before any LLM call. The initial prompt and repair prompt include required nested fields, allowed top-level fields, unit guidance, and a strict rule that schema-extra fields must be removed.

Validation errors are grouped into missing required fields, schema-extra fields, enum errors, and type errors. Repair prompts use those groups directly so the model can correct omissions and remove extra keys without changing the schema.

## Scenario Reflection Update

The flow now separates schema validation from semantic scenario reflection validation. A World Config can pass schema validation but still fail if it does not represent required user conditions such as Kickboard obstacle, path blocking, or pedestrian crossing.

Natural-language prompts are first converted into scenario intent and scenario requirements. Those requirements are added to the prompt package, used for RAG retrieval query expansion, and checked after schema validation.

## Output Contract Update

Before generation, the prompt builder adds a World Config output contract. The repair loop repeats the same contract and asks the model to preserve valid parts, add missing required nested fields, remove extra fields, and satisfy scenario requirements.

## Scenario Repair Loop

If schema validation passes and scenario reflection fails, the next repair attempt uses a scenario repair prompt instead of schema repair. The scenario repair prompt lists missing requirements by schema path and asks the model to preserve valid JSON while adding only the missing scenario details.
